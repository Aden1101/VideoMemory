puis « pourquoi on ferait pas 0.1 comme scal3r ? »

**Réponse (vérifié dans le code + papier/repo LaCT) :**
- **Nous : `g_init = 0.0`** (`video_memory.py` L208). `_init_modulation_params` zéro-init poids ET biais de `proj`, gate bias = 0 -> `gate ≡ 0` quelle que soit l'entrée -> `mem_out ≡ 0` -> bit-identique baseline AF au step 0. C'est le do-no-harm. (gate ~6e-4 au step 805 = il a à peine décollé.)

- **LaCT : design différent** (vérifié dans `causal_lact_with_sliding_window_attn.py`) : gate per-head SiLU `silu(ttt_scale_proj(x)) · o_norm(f_W(q))`, init PyTorch par défaut, PAS de do-no-harm. ## VRAM profiling : design + calibrations

**Aden :** « dis moi quelles sont tes idees pour le profiling »

**Réponse (design) :** mesurer le VRAI step de training (pas un proxy). Orchestrateur `profiling/profile_vram.py` -> 1 sous-process par combo {1,2,3 layers} × {read-only, read+write}, hook trainer `_vram_profile_tick` (reset_peak après warmup -> `max_memory_allocated`/`reserved` -> print `[VRAM_PROFILE]` -> exit). Idées clés : write-tax par soustraction (read+write − read-only), pente par layer, pente par durée (problem B), séparer pic-step vs pic-save (l'OOM 805 était sur la save FSDP), knob fp32 Newton-Schulz, gestion OOM = résultat valide. `MEMORY_LAYERS` rendu configurable via env `MAG_MEMORY_LAYERS`.

**Calibration durée (Aden : « 5s = combien de frames ? ») :** VAE `pixel = 1 + 4×(latent−1)`, export 16 fps. Donc **latent ≈ 4 × secondes**. Vérif : job 240s = `num_output_frames: 960` -> 239.8s. Donc **5s ≈ 21 frames latentes = 1 chunk** (`streaming_chunk_size: 21`), 10s ≈ 42, 15s ≈ 60 (= fenêtre training réel).

**Granularité du write (Aden : « on write chunk par chunk ? pas frame par frame ? »)** : ni l'un ni l'autre. Le chunk de 21 frames est découpé en **blocs de `num_frame_per_block=3`** ; le write a lieu **une fois par bloc de 3 frames** (agrège les ~4680 tokens du bloc en un rank-update). Donc 5s = 7 writes, 15s = 20 writes, 240s = 320 writes. Récurrence courte (bonne nouvelle méta-grad), mais chaque pas est lourd (30 blocs backbone + write graph).

## Le bug du prompt-switch dans le profiling

**Aden :** « c etait quoi le probleme avec le prompt switching ? »

**Réponse :** `dmd_switch` change le prompt au milieu du clip (`switch_choices: [21, 39]`), et le trainer exige `switch_frame < max_length` (L711). À `max_length=21` (5s = 1 chunk), aucun switch valide -> ValueError. Conceptuellement : un switch a besoin d'un segment avant ET après -> **minimum 2 chunks**. Donc le "5s first" littéral est infaisable avec `dmd_switch` ; minimum switch-able = **42 frames (10s), switch à 21** (la marque 5s). On profile à 10s. (Aussi corrigé : `torchrun` nu pointait vers le python système sans omegaconf -> `<longlive>/python -m torch.distributed.run`.)

**1 vrai data point propre obtenu :** read-only, 1 layer, 10s = **44.7 GiB alloc / 46.4 GiB reserved** sur 48 GiB (96%, très serré). Puis charlesgirardot a pris le GPU 1 (21.4 GiB) -> sweep contaminé, OOM bidons, arrêté. Pas de GPU propre depuis.

## Gating adapté vidéo (formalisation)

**Aden :** sa superviseuse trouve le scale/shift de Scal3R malin pour leur problème 3D ; LaCT l'utilise-t-il ? « pourrait on faire quelque chose de plus adapte a la video ? »

**Réponse :** LaCT n'utilise PAS le scale/shift (juste un gate SiLU per-head). Notre gating vient de VGGT (3D bidirectionnel) = mismatch pour de la vidéo causale (dérive d'identité croissante en t). Proposé un gating vidéo-natif (doc propre : `reference/video_adapted_gating.md`) :
- (A) AdaLN **temporel** : concat `φ(t)` -> le réseau apprend une rampe `g(t)` croissante (analogue exact du scale/shift mais sur NOTRE axe). Justif : accumulation d'erreur AR `e_{t+1}=(1+ρ)e_t − κg_t e_t + η` -> correction ∝ erreur -> gate doit croître.
- (B) sélectivité **mouvement** : concat `m = MLP(q_t − q_{t-1})`.
- (C) feedback de dérive : `g = g_max·σ(g_raw + α‖ô‖)` (optionnel, risque de boucle).
- **Slow-weight only -> aucun lien avec problem B**, testable sans GPU-régression. Reco : commencer par (A) seul (~10 lignes, do-no-harm préservé).
