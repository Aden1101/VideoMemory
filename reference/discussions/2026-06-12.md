## Explication détaillée du scatter slide 3 (`scatter_dc_rank.png`)

**Aden :** « peux tu me reexpliquer le graphe slide 3 en detail et comment on a calcule etc ».

Figure : « Spatial Frequency Structure vs. Rank, 360 Heads ». X = Spatial DC Energy Fraction (E_DC), Y = SVD Effective Rank, **r = −0.827**.

**Un point = une tête d'attention.** 360 = 30 couches × 12 têtes. Pour chaque tête on prend sa matrice de clés `K` du cache, taille **1560 tokens × 128 dims** (1560 = grille spatiale d'une frame, 30×52). On en tire deux scalaires (x, y). Agrégation sur les **5 vidéos** de la base.

**Axe X — E_DC (uniformité spatiale, via DCT 2D) :**
1. Pour une dim d'embedding `d`, les 1560 valeurs (1 par token) sont remises sur la grille **30×52** → une petite image `g(i,j)`.
2. DCT 2D : `X_{u,v} = α_u α_v Σ_{i,j} g(i,j) cos(π(2i+1)u/2H_g) cos(π(2j+1)v/2W_g)`. Décompose en fréquences spatiales ; `X_{0,0}` = terme DC (composante uniforme).
3. Fraction d'énergie DC : `E_DC = |X_{0,0}|² / Σ|X_{u,v}|² ∈ [0,1]`. Proche de 1 = carte lisse/plate ; faible = carte détaillée/texturée.
4. Moyenne sur les 128 dims : `E_DC^{(h)} = (1/128) Σ_d E_DC^{(h,d)}`. → droite = uniforme, gauche = détaillé.

**Axe Y — r_eff (complexité, via SVD) :**
1. SVD de `K` (1560×128) : `K = U Σ Vᵀ`, valeurs singulières σ₁ ≥ σ₂ ≥ …
2. Rang effectif = nb de σ au-dessus de 10 % de la plus grande : `r_eff = #{i : σ_i > 0.1 σ_1}`. Élevé = beaucoup de directions (riche) ; faible = sous-espace petit (compressible). → haut = complexe, bas = simple.

**Le scatter :**
- `r = −0.827` = Pearson `cov(x,y)/(σ_x σ_y)` sur les 360 têtes. Forte corrélation négative : uniforme (E_DC grand) ↔ bas rang ; détaillé (E_DC petit) ↔ haut rang.
- Ligne pointillée à E_DC ≈ 0.35 sépare deux familles : **Low-DC (bleu, n=231)** détaillées/haut-rang ; **High-DC (rouge, n=129)** uniformes/bas-rang.
- Point méthodo clé : **DCT (fréquentiel) et SVD (algébrique) sont deux méthodes indépendantes** ; leur corrélation à −0.83 montre qu'elles mesurent la même chose (la complexité du contenu), donc le signal est réel, pas un artefact.

**Pourquoi ça répond à "où vit l'identité" :** le sujet (visage, détails fins) = partie **complexe/détaillée** = cluster low-DC/haut-rang. La partie uniforme/bas-rang porte l'info globale et lente (fond). Donc figer/compresser les composantes simples préserve le **fond**, pas l'**identité** : il faut agir sur la partie complexe du cache. C'est la justification de cibler la mémoire.

### C'est quoi "Cross-Head Variability" (panneau bas de perdim) ?

**Aden :** « c est quoi cross head variability ? c est genre la variance des differentes valeurs pour une dimension ? ».

Presque, mais pas la variance des valeurs brutes : c'est l'**écart-type, à travers les têtes, de la *fraction DC* d'une dimension**. Source : `embedding_dim_analysis.py::plot_dim_consistency`.

- `profiles` = matrice [n_têtes=84 (7 couches × 12 têtes), 128]. Valeur = fraction DC de la dim dans la tête (DCT 2D sur 30×52, `energy[0,0]/total`, moy. 2 frames × 5 vidéos).
- Haut = `profiles.mean(axis=0)` (moyenne DC par dim sur les têtes). Bas = `profiles.std(axis=0)` = **Cross-Head Variability** (écart-type par dim sur les têtes).

Interprétation : faible variability = toutes les têtes d'accord sur le rôle de la dim (consistant) ; élevée = rôle head-dependent (uniforme dans certaines têtes, détaillé dans d'autres). Sur la figure : bas à gauche (dims détaillées, consistantes), plus haut à droite (dims uniformes, plus head-dependent). → justifie le masque **par-tête ET par-dim** (pas global) de la slide 7.

**Suite (Aden : « on a à peu près les mêmes dims low-dc / high-dc dans chaque head ? »)** : à peu près, mais seulement moyennement. Le `cross-head r = 0.42` (`plot_cross_head_correlation`) = `np.corrcoef(profiles)` puis **moyenne du hors-diagonale** = corrélation moyenne, entre paires de têtes, de leur profil DC sur les 128 dims. r=1 → mêmes dims uniformes/détaillées partout (masque global OK) ; r=0 → sans rapport ; r=0.42 → squelette partagé + beaucoup de variation par tête. Les dims à faible cross-head variability = le squelette (tirent r vers le haut), celles à forte variability = head-dependent (tirent vers le bas). C'est pour ça qu'il faut un masque par-tête/par-dim et pas global.

**Suite (Aden : « c'est quoi le cross head en terme de calcul ? »)** : moyenne de Pearson par paire de têtes, calculé sur les 128 dims.

- `profiles[h,d]` = [84 têtes × 128 dims], valeur = fraction DC.
- Par paire (A,B) : `r_AB = Σ_d (a_d-ā)(b_d-b̄) / (√Σ(a_d-ā)² · √Σ(b_d-b̄)²)`, somme **sur les 128 dims** (= cosinus des profils centrés ; ā = moyenne du profil sur les dims).
- `np.corrcoef(profiles)` = matrice [84×84] de tous les `r_AB` ; on moyenne le triangle sup. hors-diag (`C(84,2)=3486` paires) → 0.42.

Point clé : Pearson **à travers les dims** (128 points), **pour une paire de têtes**, puis moyenne **sur les paires**. À ne pas confondre avec la cross-head variability = `profiles.std(axis=0)` (std **par dim** à travers les têtes).

### W_proj change-t-il à l'inférence ? Non (fast-weights vs slow params)

**Aden :** « wproj change ou pas a l inference avec les pas de gradient ? … inert warm start c'est pour l'entrainement externe ? ».

### C'est quoi un meta-gradient ?

**Aden :** « c'est quoi un meta gradient ? ».

Le gradient d'une loss externe par rapport à des params qui n'agissent **qu'à travers une mise à jour qui est elle-même un gradient** → un gradient-à-travers-un-gradient = **second ordre** (Hessien).

Chez nous : le write est `W_{t+1} = W_t + ∇_W⟨f_W(k),v⟩` (la maj contient déjà un gradient). Les write-only params (`k/v proj`, `k_norm`, `lr`) ne touchent la loss qu'en **façonnant ce pas** → pour `∂L/∂θ_write` on dérive à travers le pas → apparition du Hessien `∇²_W ℓ` (le `A_r = ∂WN·(I+∂Muon·∇²_W ℓ_r)` de la slide 24), + BPTT sur les chunks (`∏ A_r`) + dériver à travers Muon.

Contraste : gradient normal (read) = chaîne directe `q→f_W(q)→o→L`, pas cher. Meta-gradient (write) = à travers le pas d'update, cher + fragile. C'est le mécanisme de **MAML**. Intuition : on n'apprend pas un poids, on apprend **une règle d'apprentissage**. En Phase 1 le write tourne `no_grad` → le meta-gradient s'annule → `θ_write` reste à l'init.

### Teacher forcing : ça change quoi ?

**Aden :** « ca change quoi teacher forced ? ».

Teacher forcing = à l'entraînement, nourrir le modèle avec la **vérité terrain** au lieu de ses propres sorties.

- **Self-rollout (nous, Self-Forcing/DMD)** : le générateur conditionne sur **sa propre génération**, KV cache **réécrit en place** → graphe profond, in-place → meta-gradient du write **infaisable** (problem B).
- **Teacher-forced (LaCT, TTT-Video)** : vraies frames en contexte, **un seul forward**, attention **recalculée** chaque passe, pas de cache in-place → graphe propre, différentiable bout-en-bout → **meta-gradient du write calculable**. D'où « LaCT meta-train le write, mais teacher-forced ».

Le prix : **exposure bias** (décalage train/test) — à l'inférence le modèle voit ses propres générations qui dérivent, qu'il n'a jamais vues à l'entraînement ; et ça **évite justement la partie self-rollout** où la dérive arrive. Tout l'intérêt de Self-Forcing/DMD est de corriger cet exposure bias en s'entraînant sur sa propre distribution → teacher-forcer le réintroduirait. Tension : teacher forcing → meta-gradient facile + exposure bias ; self-forcing → exposure bias réglé + meta-gradient dur. C'est pile problem B.

### Cache in-place concrètement : ce qu'on a que LaCT n'a pas

**Aden :** « Pas de mutation de cache in-place, ça veut dire quoi concrètement, qu'est-ce que nous on a que LaCT n'a pas ? ».

Vérifié dans `causal_model.py` (~267-286). Le KV cache est un **buffer de taille fixe** (3 sink + 9 local FIFO). Chaque pas : `temp_k = cache.clone()`, `temp_k[:, write_start:end] = k` (écriture par slice), roll FIFO (décalage), `cache = temp_k`. Donc buffer **roulant réutilisé** : on écrit les nouveaux tokens dans des slots et on **évince** les vieux.

Pourquoi ça casse le meta-gradient (backprop chunk *s* → écriture *t*) :

1. **Éviction FIFO jette l'info** : le token écrit en *t* est sorti du cache en *s* → chemin de gradient **structurellement coupé**.
2. **Écritures slice / réécriture de buffer** = ops in-place ; à la profondeur d'un self-rollout (centaines de pas), garder le graphe explose / casse.
3. **Self-rollout** = sortie *t* → entrée *t+1*, graphe à centaines d'étages.

Ce qu'on a en plus : **cache KV fixe, roulant, éviction FIFO, écrasé à chaque pas auto-régressif** (indispensable pour la vidéo longue : un cache qui grossit ferait exploser la mémoire) → détruit les tenseurs dont le meta-gradient a besoin. Ce que LaCT a en plus : **recompute l'attention complète sur un contexte gardé en entier, une passe teacher-forced, rien d'écrasé** → write entraînable de bout en bout (prix : exposure bias, pas de self-rollout).

### Coût vs faisabilité : c'est les deux, et ils sont liés

**Aden :** « notre problème c'est que le calcul est trop lourd, ou que le kv cache change constamment donc on peut pas faire le calcul vu qu'il s'étale sur toute la vidéo, ou les deux ? ».

Les deux, mais à distinguer :

1. **Coût** (lourd/long) : Hessien + BPTT + Muon. **Générique** (LaCT le paie aussi). Si c'était le seul problème, on pourrait payer (compute, checkpointing). C'est un **prix**, pas une impossibilité.
2. **Faisabilité** (à nous) : même avec compute infini, le calcul exact est **impossible** — écritures in-place cassent l'autograd, éviction FIFO **jette** les tenseurs. Le calcul s'étale sur toute la vidéo, le cache ne garde que 12 tokens → chemin de gradient **structurellement coupé**.

**Le lien** : on évince PARCE QUE tout garder sur une vidéo longue coûte trop cher (mémoire). Donc (1) poussé à l'échelle vidéo longue **force** le cache roulant → crée (2). Clip court (LaCT) = on peut tout garder → cher mais faisable.
